# panel/

- **Stacking is deliberately low: Jobs button `z-index` 9, frame 39.** The Web UI's modal dialogs are z-50; a huge z-index put the open panel over their buttons (the Save button in Settings could not be clicked). The button sits under the Web UI's navigation (`aside`, z-10): on narrow windows the open menu spans the width and its close button lands exactly where the Jobs button is, so at z-40 the button covered it.
- **The Jobs button is a 40px round ghost icon** aligned with the Web UI's logo (`top`/`right` 16px). Its badge is a quiet dot while jobs only run and an amber count of plans waiting for review; review is the one state meant to catch the eye. The count is still running + review in the `aria-label`.
- **The Web UI routes with the hash, and Settings pages are `#/settings...`.** `inject.js` hides the button and frame (`ajp-away`, frame inert, panel told it is hidden) while the hash starts with `#/settings`. **`hashchange` is not enough:** the Web UI (SvelteKit) navigates with `history.pushState`/`replaceState`, which fire no event, so `inject.js` also compares `location.href` every 300 ms (plus `popstate`/`hashchange`) and re-applies only when it changed. Don't monkey-patch `history`. It never changes the saved open flag, so leaving Settings restores exactly the earlier state. If the Web UI changes its routes, this prefix is the thing to update.
- **Empty trash is a two-click confirm inside the panel, not `window.confirm`** (a native confirm focuses OK, so Enter would delete). The first click only arms the button for 5 seconds, and a click within 400 ms of arming is ignored (double-click, held Enter); Restore still uses `window.confirm`.
- **`refresh()` must always re-arm its timer.** Rendering runs inside a try/catch that shows "Couldn't show jobs: ..." so a render bug can't freeze the polling.
- **Plan warnings (`job.warnings`, a list of `{text, level}`) come from fixed server rules and are always shown above the review**, whatever the review says. Level `danger` (removing more than half the folder) gets the red style.
- **The panel sends the approval key, not the Web UI's API key** (ADR 0009). The user pastes it into the panel's own field, saved as `localStorage["agentJobs.approvalKey"]`; the field shows only while the key is missing or refused. The proxy must never add it: then any page that can make the browser send a request to the proxy could approve plans.
- **The model test's jobs never reach the panel:** `/jobs` drops the IDs in `test_jobs.json`, which only the launcher folder holds, so no agent or web page can hide a job from the user. Don't add a panel or proxy route that writes that list. The panel also has no Cancel: `/jobs/<id>/cancel` is the launcher's and stays out of the proxy's allow-list.
- Everything from the model (paths, step text) goes in with `textContent`, never as HTML.
- **Theme follows the Web UI, not the OS** (ADR 0014). The Web UI marks its theme with a `dark` class on `<html>`; `inject.js` watches it with a `MutationObserver`, toggles `ajp-dark` on the Jobs button, and posts `{type: "agent-jobs-theme", dark}` to the frame (also on the frame's `load`). `panel.js` sets `dark` on its own `<html>` from that; until the first message (or opened alone at `/agent-jobs`) it follows `prefers-color-scheme`. `panel.css` keys its tokens on `:root` / `:root.dark`. If the Web UI stops using the `dark` class, this is what to update.
