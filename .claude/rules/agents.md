# agents/

- **Only `server.py` may import `mcp`** (and its `anyio`/`starlette`). Everything else is standard library, because the launcher and tests import it without `uv` (ADR 0007).
- **mcp 2.x:** the class is `mcp.server.mcpserver.MCPServer`; `mcp.server.fastmcp` raises on import. The pin is `mcp>=2.3,<3`.
- **The agents server is its own process, not an mcp-proxy child** (ADR 0007). The launcher runs `uv run --script agents/server.py`, which serves streamable HTTP at `http://127.0.0.1:8002/mcp` (`--port` overrides, for tests on spare ports). A crash there must not take fetch and ddg-search down with it, which it did inside mcp-proxy. Startup errors exit with one `agents server can't start: ...` line.
- **DNS-rebinding protection is passed explicitly** (`TransportSecuritySettings`: hosts `127.0.0.1:*`/`localhost:*`, origins `http://127.0.0.1:*`/`http://localhost:*`), so a change in mcp's defaults can't drop it. A rebound page sends its own `Host` and gets 421. The transport is stateless with JSON replies, as mcp-proxy `--stateless` served the Web UI through llama-server's proxy.
- **Jobs live inside the agents server process.** It stays up between calls, so background threads work, and it dies on Exit Processes. On start, `cancel_unfinished()` marks leftovers; the launcher does the same on Exit Processes after killing it (queued/running become `cancelled`, applying/restoring become `failed` with a note to use Restore). So never start a second copy while the launcher runs: its startup marks a live apply `failed`, which lets Restore run alongside it.
- **Every path from the model goes through `Policy`.** `can_read` covers tools, `can_write` covers the sandbox minus `jobs\` and `trash\`, `can_change` covers plan operations. `is_inside` uses `realpath`, so junctions can't escape. Job IDs are checked against the exact format before they become paths. `agent_folders.json` stays outside the sandbox, so an agent can't widen its own access.
- **The launcher folder is unreadable to agents** (`api_key.txt`, `config.json`) even when a parent of it is a listed folder. `can_change` also refuses any folder that contains the launcher or the sandbox.
- **Web XOR user files, per job kind.** research and plan get web tools plus sandbox-only read/write; organize gets the listed folders, no web, and no `write_file`. A fetched page must never be able to steer an agent that can read private files, and the model must not copy listed-folder contents into the sandbox, which web jobs read. Don't combine the tool sets. Plan follow-ups can only name a folder the goal text gives, because the plan agent can't look inside folders.
- **Plan validation (`validate_plan`) is stricter than it looks:**
  - Operations may not overlap each other; the only exception is a later path under an earlier `mkdir`. Without this, one op could depend on another in ways validation can't see.
  - Moves are `os.rename` only (no cross-drive), and removals only on the sandbox's drive, because trashing is a rename into `trash\`.
  - Paths must be plain: drive-letter absolute, no `:` streams, wildcards, control characters, trailing dot or space, or device names (`CON`, `NUL`, ...).
  - Every path must be strictly inside the job's own folder (`root=job["args"]["folder"]`), checked at `propose_plan` and again in `approve`. Listing two folders must not let a plan for one touch the other, and what the user approves must stay inside the folder the job was asked to organise.
  - `propose_plan` first runs `expand_folder_destinations`: a move whose `dst` is a folder (made in the plan, or existing) becomes `folder\<name>`, and mkdirs move to the front, since models also write the mkdir after the moves into it. A 14B model writes "into PDFs" as `dst=...\PDFs` most of the time, and the overlap rule then rejected every attempt (stress test 2026-10-15: 3 of 5 organise cases never produced a plan). The expanded, explicit paths are what's saved and approved. Overlap errors also spell out the `<folder>\<file name>` form, and `ORGANIZE_PROMPT` carries a worked example.
  - `propose_plan` adds a batch (ADR 0013): the prompt asks for at most `PLAN_BATCH` (25) operations a call, because a 205-operation plan in one reply ran past `llm.chat`'s 900 s timeout (O4, 2026-10-16). Each call expands and validates the whole plan so far, so error numbers count earlier batches first. A rejected batch isn't added and earlier batches stay for a retry, but if the job ends with its last batch rejected the plan is dropped, so `result.md` can't describe a plan other than the one in `plan.json`.
  - `validate_plan` writes nothing. The same checks run again per operation in `_stop_reason` right before it executes (files may have changed since the proposal), and the first problem stops the apply.
- **Plans are approved only in the jobs panel in the Web UI, which shows the whole plan.** `apply` is not an MCP tool: a chat prompt shows only `apply(job_id=…)`, so approving there approved an unseen plan. Chat keeps `reject`, `restore` and `queue_steps`, which never apply a plan.
- **The panel's actions are HTTP routes on the agents server:** `POST /jobs/<id>/apply|reject|restore|queue`. Custom routes sit outside mcp's rebinding middleware, so each request passes `llm.check_request`: `Host` exactly `127.0.0.1:<port>` or `localhost:<port>`, and `Authorization: Bearer <approval_key.txt>` compared with `hmac.compare_digest`; anything else is 403. That is the panel's own key, never the llama API key, which other clients hold (ADR 0009); the launcher creates it, and without the file every route refuses. The reply is `{"ok", "message"}`; `ok` only says the request was authorised and handled, the message says whether the action took effect. The runner call runs in a worker thread (`anyio.to_thread`), since apply can take minutes.
- **`POST /jobs/<id>/cancel` (`JobStore.request_cancel`) is the launcher's, for the model test's Stop.** Same `check_request` guard, but it isn't an MCP tool and the proxy's panel allow-list doesn't forward it; keep it that way. Queued becomes `cancelled` at once, awaiting is `rejected`, running is only flagged (`cancel_requested`): `run_agent` checks `cancelled()` before each model call, the job writes what it has (organize skips the review), and `Worker._run_one` then marks it `cancelled`, also when it already ended `done`/`awaiting_approval`, so a cancelled plan can't be approved. A job never stops mid-tool-call, and applying/restoring are never cancelled: a half-done move must finish so Restore has a complete log.
- **`/jobs` hides the job IDs listed in `test_jobs.json` (`paths.TEST_JOBS_FILE`)**, the model test's jobs. It lives only in the launcher folder, which no agent can read or write, and there is no route or tool that adds to it, so neither a model nor a web page can hide a job from the user. A missing or damaged file hides nothing. `JobStore.delete` (the next test clears the last one's jobs) removes the job folder and `trash\<job>` with `plans._delete`, never `shutil.rmtree`.
- **The jobs panel also uses `GET /jobs` (`panel_api.jobs_payload`) and `POST /trash/empty`**, same `check_request` guard. `/jobs` sends the full `plan.json` and `review.md` only for `awaiting_approval` jobs (the user approves exactly that list; never cut it) and the last 5 steps for the rest. The list is capped at 50, but awaiting and in-progress jobs are always included before the newest others fill it, so an old plan never drops off the only approval surface.
- **Removal warnings are fixed rules, not the model's opinion** (`panel_api.removal_warnings`, sent as `warnings` for `awaiting_approval` jobs): a list of `{text, level}`; any remove gets a `warn` count, and removing more than half the folder's files adds a `danger` one. The model review rubber-stamped "delete everything" in the stress test, so the panel must never rely on it alone. Counting walks the folder without following links (a removed junction is one item). They are computed once when the plan is proposed and saved as `warnings.json`; `/jobs` reads that file, since the panel polls every 2 s and a big folder must not be re-walked each time (it computes only for older jobs without the file).
- **`runner.FILE_MOVES` is one lock around `apply_plan`, `restore` and Empty trash**, wherever each was started (panel route or chat tool). Empty trash takes it non-blocking and also refuses while any job is `applying`/`restoring`, so it can never delete files a move is using. Take it only around the file work, not around state transitions.
- **Approval is a state transition under a lock** (`awaiting_approval` to `applying`) in the one server process, so a double click can't apply a plan twice.
- **`applied.json` is written after every step (`on_step`)**, not only at the end, so a crash mid-apply still leaves a log Restore can use. Restore skips occupied or missing items and reports them instead of overwriting.
- **Trash layout is `trash\<job>\<step number>\<drive>\<path>`.** The step number keeps two removals of the same name apart. `empty_trash` never follows junctions or symlinks (`_delete` removes the link itself); don't swap in `shutil.rmtree`, which can recurse through a junction into real files.
- **Research and plan answers may cite only pages `fetch_url` read, enforced in `_source_check`, not just the prompt.** Qwen3-14B wrote reports from ddg snippets after one search and cited pages it never opened (job 20261015-165707-2a6e; the same happened on b9776, so not the build). `run_agent`'s `check` sends a final answer back, at most `MAX_CHECKS` (2) times, while it cites an unread URL, or for research also while nothing was read (a plan may read nothing). After that the answer is kept with a warning line above it and the unread URLs in the job note. A citation matches when it equals the fetched URL minus trailing punctuation, slash and fragment; a failed fetch doesn't count, and a redirect target isn't the fetched URL. URLs in code (fenced blocks, an unclosed fence to the end, inline backticks around a command) aren't citations, but an inline span that is only a link (a source written as URL: then the link in backticks, as Qwen3.6 and gpt-oss list sources) is one, and must have been read like any other: a plan's `git clone ...git` sent the model back twice to fetch a URL robots.txt blocks. The accepted cost is that a citation in backticks escapes the check.
- **Research and plan prompts start with `Current date: ...`** (`_dated`), the same date-only line the proxy adds for the Web UI (ADR 0004). Agent jobs call llama-server directly and miss the proxy's line, so the model guessed the year of dated pages (stress R1 2026-10-15 dated v0.7.0 "October 15, 2023"). Giving jobs the `time` MCP tool instead was rejected: the 14B model skips tools it isn't forced to use, as it skipped `fetch_url`. Organize has no date line.
- **Context budget:** `MAX_CALLS` 40, `MAX_SECONDS` 20 min, tool results cut to `MAX_RESULT_CHARS` (6000), and `_trim` replaces the oldest tool results and tool-call arguments (a plan batch is all arguments) with stubs once the history passes the job's budget, always keeping the last 4 messages. The budget is `context_chars(n_ctx)`: half the context llama-server reports on `/props` at 3 characters a token, never above `CONTEXT_CHARS` (40000), which is also the fallback when `/props` can't be read. `--fit` gave gemma-4-26B 8704 tokens and a 40000-char history got HTTP 400 (2026-10-16). `llm.n_ctx` takes the smaller of the top-level and `default_generation_settings` values (builds differ; the second is per slot). The arguments stub must stay valid JSON (`ELIDED_ARGS`), since llama-server parses it. A model or network error after the first turn ends the job and keeps what it has. `server.py` limits `job_result` to `MAX_FILE_CHARS` (8000) per file so a big plan can't flood the chat model.
- **`steps.jsonl` is the jobs panel's progress feed**, one line per tool call (`run_agent`'s `on_step`) plus `Stopped:`/`Reviewed the plan`/`Sent back to read its sources`. Step text can come from web pages or file names: `append_step` strips control characters and caps at 200, and the panel must show it with `textContent`. Writing it is best-effort and never fails a job. It is not `steps.json` (the plan job's follow-up jobs).
- **`propose_steps` with no valid step is an error and keeps the earlier steps.** Ministral called it with 3 steps, then with `[]`, and `steps.json` ended empty (2026-10-16).
- **Tool errors go back to the model as strings** (bad arguments, no access); they never raise out of the loop.
- **`llm._post` turns every transport failure into `RuntimeError`**: HTTP errors, a reply cut off mid-way (`http.client.IncompleteRead` is not an `OSError`) and a non-JSON body. `run_agent` only treats `RuntimeError`/`OSError` as network errors that keep a job's work, so anything else failed the whole job.
- **`JobStore.list` skips a `job.json` without an `id`** (and unreadable ones), and `/jobs` ignores a `steps.json` that isn't a list: one damaged file must not take the Jobs panel down.
- `mcp_call` posts one JSON-RPC `tools/call` without `initialize`, for `fetch` and `ddg-search` on the UVX proxy. That only works because mcp-proxy runs with `--stateless`.
