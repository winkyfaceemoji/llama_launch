# launcher.pyw and launcher_app/

- **One module per area (ADR 0020); `launcher.pyw` is only the entry point.** Paths come from `paths.ROOT` (the repo root), never a module's own folder: `config.json`, the keys, `agents/` and `proxy.py` live there, and `is_own_process` recognises our processes by that folder. **Colour names are rebound live:** a GUI module does `from .theme import BG, ...` then `theme.follow(globals())`, so `set_palette` updates its copies. A module that imports colours without following them freezes the palette it was imported with and quietly breaks live theme switching.
- **`ConfigStore` (`config.py`) is the only reader and writer of `config.json`.** It checks every value of the keys the launcher uses on load and before each write; a bad one raises `ConfigError` naming the key, and the entry point refuses to start, writing nothing (a fallback would have been written over the real value at the next save). Invalid JSON, an unreadable file and a BOM refuse too (proxy.py reads the file as well, so the launcher can't just skip a BOM). With every value checked, `self.config.get("theme", "system")` needs no fallback of its own. A preset that isn't an object must be a string (`load_presets` takes it as an old-style command). Keys it doesn't own (`mcpServers`, which mcp-proxy reads) pass through the store untouched; `remove_stale_agents_entry` still drops the old `agents` entry from it, as before. In the window every write is `self._save(key=value)`, which shows a disk error or a refused value in a dialog (None removes a key; no arguments saves in-place edits by `migrate_uvx_command`, `set_prompts` and the like); `self.config` is the store's dict: read it, or edit it in place and then call `self._save()`.
- **`Selection` (`selection.py`) owns the model and preset choice.** Every change returns a `View` (both dropdowns' items and selection, the launch command, the model's files); the command is derived from the latest scan every time, never kept, so a model whose files changed can't launch stale. Rules: picking a model, even the same one, resets the preset to Auto; a preset survives Refresh while its model does; startup doesn't write `last_model`, a pick or a Refresh fallback does (`remember_model`); a model whose name starts with "(" gets no presets and is never remembered, as in the single-file launcher, which took such names for placeholders; preset changes save the whole dict through `save_presets`; refusals are `PresetError(kind, title, message)`, shown as `messagebox.show<kind>` (`error`, `warning` or `info`, mapped in `_refused`). `delete_preset` asks its `confirm` only after its checks.
- **Views (`views.py`) are rebuilt on every switch** (`CommandLauncherGUI._switch`): `SetupView`, `HomeView`, `RunningView`. A fresh running view can't carry dots, labels, an open Connection row or old log lines over from the last run. State that must outlast a view lives on the window: the Auto-scroll choice (`autoscroll_var`) and the update notice's builds (`_update_builds`), which both home and running show. Views call the window's public methods (`launch`, `stop`, `open_settings`, `refresh_models`, `pick_model`, `pick_preset`, `open_preset_menu`, `start_model_test`, `start_update`, `finish_setup`). The process code keeps writing to `self.llama_log`, `self._llama_label_var`, `self._elapsed_var`, `self.test_btn` and friends: `_enter_running_state` points those names at the new running view (ADR 0021 keeps that code's logic as it was). A line for a previous run's view (a reader thread outliving its run) is dropped by `RunningView.append`.
- **`self.running` is the running flag**, set in `_enter_running_state` and cleared in `stop()`. Settings' roll back and the Prompts lock read it.

- **Child output must keep draining.** Each `Popen` uses `encoding="utf-8", errors="replace"` and `_stream_output` reads until EOF. If the reader thread dies (a decode error under Windows' cp1252 default can do this), the pipe fills and llama-server blocks on its next log line, which looks like the model hanging mid-chat.
- **tkinter is not thread-safe.** Background threads (readers, health poll, tray) must hand UI work to the main thread with `widget.after(0, ...)`.
- **Every launch command goes through `build_launch_command`**, which appends `--api-key-file` (ADR 0005). Don't start llama-server from anywhere else, and never ship a preset with any `--tools` or `--agent`: newer builds' built-in tools are only file, shell and OS tools that any web page could call, and an unknown tool name stops llama-server from starting (b11636 dropped `get_datetime`; ADR 0011).
- **The keys are never displayed** (only copied) and never written to `config.json`, whose contents the UVX proxy also reads. The approval key (`approval_key.txt`, ADR 0009) is created at startup next to the API key; only the Jobs panel sends it.
- **Auto preset:** `AUTO_COMMAND` must not set `-c` or `-ngl`; setting either turns `--fit` off for that value (ADR 0001). `load_presets` always replaces Auto with the code's version (a copy gets saved into `config.json` whenever presets are edited, and would otherwise go stale), and `Selection` refuses to edit or delete it (an edit would be undone at the next start without a word).
- **Preset selection resets to Auto** on startup and on every model change; other presets are manual overrides and are not remembered (ADR 0002).
- **Preset `models` are case-insensitive substring keywords**, not exact filenames, even though the dialog stores full names. A short keyword like `"qwen"` matches every Qwen file.
- **Vision models:** an `mmproj*.gguf` is only paired with models in the same *subfolder*; one sitting in the root models folder is ignored. Display names come from the file name, and the first one found wins (root before subfolders, then alphabetical).
- **`_free_port` only kills our own leftovers** (`is_own_process`: any `llama-server.exe`, or a command line containing this folder's path). Anything else on 8080/8081/8001 aborts the launch with its name and PID; on 8002 it only skips the agents server. It runs `netstat` and a PowerShell CIM query on the UI thread, so the window stalls briefly when a port is taken.
- **mcp-proxy runs through `mcp_guard.py`** (`uv run --no-project --with mcp-proxy==0.13.0 python <this folder>\mcp_guard.py --named-server-config <this folder>\config.json ...`), so `is_own_process` recognises it by this folder's path. The wrapper adds the Host check mcp-proxy lacks by wrapping the app passed to `uvicorn.Config` (ADR 0012). Bumping the mcp-proxy pin means re-running the live probe: `Host: evil.example:<port>` must get 421.
- **`uvx_command` uses `{config}` and `{guard}` placeholders** for the config and wrapper paths, resolved at launch by `resolve_uvx_command`, so moving the folder doesn't break MCP. Saved configs keep their own command: `migrate_uvx_command` swaps only the exact old default (`uvx mcp-proxy ...`) for `UVX_COMMAND`, and an edited command stays unguarded.
- **The agents server is a fourth process the launcher starts itself** (`_start_agents_server`, after the UVX proxy): `uv run --script agents\server.py --port 8002`, list args with `CREATE_NO_WINDOW` (no shell, so nothing else hides uv's console), cwd = this folder. Its lines go to the UVX tab prefixed `[agents] `, and `health_status` names it "agents server". It used to run inside mcp-proxy, where one failure killed fetch and ddg-search too (ADR 0007). `remove_stale_agents_entry` deletes the old `agents` entry from `config.json`'s `mcpServers` on launch.
- **`_kill_all` cancels unfinished agent jobs last, after all four processes are dead** (the agents server is killed before `cancel_unfinished`). Only once it's gone is the launcher the sole writer of job files. The call is wrapped so a failure there (unreadable sandbox) can't stop the exit.
- **The agents feature is optional: sandbox or `agent_folders.json` errors must never stop the launcher from starting or exiting.** `ensure_dirs` at startup catches `OSError` into `_agents_error` (then the agents server isn't started), `_start_agents_server` logs any failure (port held by a stranger, no `uv`) and lets the launch carry on, `FoldersDialog` shows its own I/O errors, and `_kill_all` swallows the job cleanup. `FoldersDialog` is a child of Settings and its `_close` hands the grab back to Settings (Tk doesn't restore it on destroy).
- **One health poll per launch (`_poll_gen`).** `_stop_health_poll` only clears a flag the loop checks every 3 s, so an Exit and quick relaunch used to leave the old loop running beside the new one (two browser tabs, stale status). Each start bumps `_poll_gen`; a loop stops when its number is no longer current, and its UI updates (`on_ui`) are dropped once it isn't.
- **Health:** `health_status` reports a crashed child by name before anything else; llama-server's `503` while loading shows as "loading model", not "offline". The agents server is optional, so its crash shows for one poll only (`shown`), then llama's status returns and the crash stays in the UVX tab as an `[agents] exited (code N)` line. Stop Servers stops the poll before killing, so its own kills aren't reported as a crash.
- **Every exit stops the tray icon** (`_force_exit`): a pystray icon whose process ends without `stop()` stays in the tray until the mouse passes over it. `stop()` only posts a message; the tray thread removes the icon, so `_force_exit` joins it (2 s at most) before `destroy()`, inside a `try` so the window always closes.
- **A failed launch shows its reason in a dialog**: `stop()` replaces the running view with home, so the `LAUNCH FAILED` line alone was never seen.
- `_kill_proc` uses `taskkill /T` because with `shell=True` the Popen PID is `cmd.exe`; `proc.kill()` would kill only the shell and leave llama-server running and holding VRAM. `/T` on the `uv` PID does reach the venv `python.exe` pair under it (checked for both uv launches).
- **The window's X stops every server and exits** (`_force_exit`, same as the tray's Exit; ADR 0016). Nothing hides the window to the tray: hiding with servers running is how leftover servers and stale launchers piled up.
- **One launcher per Windows session** (ADR 0017): the entry point calls `claim_instance` before building the window; a second launcher signals the first's show event and exits. The check is in `__main__` only, so tests and `dev/gui_shot.py` skip it. It isn't per folder: a launcher started from a worktree while the user's runs only brings the user's window up. Without it, a second launcher's `_free_port` killed the first one's servers as our own leftovers and left the first holding dead handles.
- **Icon (`icon.ico`, drawn by `dev/make_icon.py`):** without an AppUserModelID, Windows groups a pythonw window under pythonw.exe's icon on the taskbar, whatever icon the window sets. The entry point calls `SetCurrentProcessExplicitAppUserModelID` before `tk.Tk()`; set after the window has shown, it stays in the Python group (checked). It's in `__main__` only, so `dev/gui_shot.py` windows still show Python on the taskbar. `iconbitmap(default=...)` gives every dialog the icon; the tray loads the same file. The icon uses `PALETTES["dark"]` whatever the theme, so it reads on light and dark taskbars.
- **Settings is a drill-down** (`SettingsDialog`): General plus the Agents, llama.cpp and Advanced pages, all built once and swapped by `_show`, so unsaved values survive page changes; the dialog's height follows the page (`winfo_reqheight`), so there are no Settings height constants. **Every page's changes wait for Save** (folder, Web UI, theme, UVX command). The theme previews through `_preview_theme`, which sets `_theme_preview`: `_watch_windows_theme` follows the preview while it's set, or System mode would undo it within 3 s. `_cancel` (Cancel, the X, Esc, and before a roll back) restores the saved theme. Agent folders and Prompts save in their own dialogs, never through Settings' Save.
- **Outlined vs plain ghost buttons:** an action that stands alone beside text or a field (Settings, Refresh, Browse, the Settings rows' Manage…, Edit…/View… and Roll back) is an `outline_btn`, so it reads as a button and not a label. Buttons in a dialog's bottom row (Cancel, Close, Remove), the Connection toggle, Copy and "⋯" stay plain `small_btn`s. Pack or grid the returned frame; `.button` is the button.
- **Popup menus** (`popup_menu`): the model dropdown's list and the preset "⋯" menu are one borderless themed popup; a pick closes it before running the command, so a dialog the command opens isn't left under it.
- **The Connection row** (Agent API address and the keys, each with Copy) is collapsible and starts closed on every launch (the running view is built fresh).
- **Logs are tabs over one area** (`RunningView._log_tabs`: Text -> `LogTab`; `show_log` raises one). A line matching `log_line_is_error` that arrives on a tab other than the shown one packs that tab's red dot; showing the tab or a new launch clears it. llama-server's harmless `http client error` lines match too, so its dot lights often.
- **Keyboard:** Enter (`_on_return`) launches only on the home view (`isinstance(self.view, HomeView)`); Esc (`bind_all`, `_on_escape`) runs the dialog's own `WM_DELETE_WINDOW` command when it has one (Update and Test refuse to close while working), else destroys it; Ctrl+, opens Settings. Enter and Ctrl+, are bound on the root's own tag, so they never fire from a dialog (a separate toplevel, grab or not: TestDialog has none).
- **Scrollbars** are ttk with a custom `Vertical.TScrollbar` layout (trough + thumb, no arrows) in `apply_ttk_style`, which `apply_theme` reruns; plain `tk.Scrollbar` is drawn natively on Windows and ignores colours, so don't use it.
- Log tabs keep their last `LOG_MAX_LINES` (5,000) lines: `RunningView.append` calls `trim_log` after each line, since an untrimmed pane made a long session's window slow (not the model). The Update and Test dialogs' logs are short-lived and not trimmed.
- **WinGet calls (llama.cpp updates):** every call passes `--source winget --disable-interactivity`, so a prompt makes WinGet fail instead of hanging. Only upgrade and install pass `--accept-package-agreements --accept-source-agreements`, and only after the user clicks Update or Roll back; the notice on home says updating accepts the package's terms (on the running view, where Update is disabled, it says to stop the servers instead). `check()` (list) runs at every start and must never accept anything.
- **Prompts (`PromptsDialog`, from Settings) are editable only while the servers are stopped** (`self.running` when Settings opens; Settings is modal, so the state can't change underneath). The proxy and agents server read prompts once at startup, so the lock is what makes the read-only view while running show exactly what they use; don't add live reload without changing that. Save goes through `set_prompts` (refuses what `agents.prompts.check` refuses; drops agent prompts that are blank or the shipped text so later shipped improvements reach them), then `backup_config` (`config.json.bak`, gitignored, the only undo since `config.json` isn't in git), then `self._save()`. Like `FoldersDialog`, it hands the grab back to Settings on close.
- **Updates and roll back only while the servers are stopped:** Windows locks a running `llama-server.exe`. The running view shows the update notice with Update disabled, and Settings gets `on_rollback=None` then.
- **The build check runs llama-server on spare port `18081`** (never 8081) and always kills it with `taskkill /F /T` in a `finally`, even on timeout or an exception; otherwise it keeps holding VRAM.
- **`previous_build` is the only update state** (`config.json`, `"b9776"`): set right before an update, cleared after a successful roll back so the startup notice offers the newer build again. A failed roll back leaves it, so Settings can retry.
- **Model test lock (`model_test.lock`):** the launcher writes it with a fresh random token (`write_test_lock`) right before starting the harness; the proxy pauses Web UI chat while it exists and lets through only requests whose `X-Model-Test` header matches the token, which the harness reads from the file. It's cleared when the test ends (done or failed), at the end of Stop, at launcher startup and at the end of `_kill_all`, so a crash can't leave chat paused. `clear_test_lock` retries (the proxy may hold the file open) and never raises.
- **The harness runs under `python.exe`, never `pythonw.exe`** (`model_test_command` swaps it), with `-u` and `PYTHONIOENCODING=utf-8`: pythonw has no console streams, so its output wouldn't reach the dialog. `CREATE_NO_WINDOW` keeps python.exe's console hidden.
- **Stop order (`TestDialog._stop_sequence`):** kill the harness tree (`taskkill /F /T`) so it starts no more jobs; `POST /jobs/<id>/cancel` on the agents server for every ID in `test_jobs.json` (approval key, `Host: 127.0.0.1:8002`; failures are only logged); delete `test_temp_dirs()` (the stress harness's `%TEMP%\agent-stress*`); remove the lock last. A stopped test writes nothing to the report. The button asks first and runs it in a thread.
- **Stop Servers during a test stops it first**: `_kill_all` calls `TestDialog.stop_now()` (same sequence, no question, on the UI thread) before killing anything, since the cancels need the agents server alive. `TestDialog` has no grab so Stop Servers stays clickable; the Test button is disabled while a test runs and whenever the health poll isn't `ok`.
- **Theme (ADR 0014):** `set_palette` rebinds the colour constants (`BG`, `TEXT_PRI`, ...) from `PALETTES`, and widgets read them when they're built, so the palette is set in `__init__` before any screen. `apply_theme` switches live by walking every widget and swapping each colour option that holds an old-palette colour for the same role's new one. Hence:
  - **Every colour is unique within its palette** (a test checks). Where two roles should look the same, they differ by one step (`BG_PANEL` is one off `BG`).
  - **No hex literals outside `PALETTES`,** and **no colour as a default argument or captured at start** (a default is bound once, at definition): look it up at call time, as `flat_btn`/`small_btn` and the health label (`_palette[role]`) do.
  - Title bars: a `<Map>` class binding on `Tk` and `Toplevel` sets the dark title bar for every window as it shows; `apply_theme` redoes it for open ones. `set_dark_title_bar` skips borderless (`overrideredirect`) windows: its `SWP_FRAMECHANGED` call drops Tk's pending move, which put the dropdown list at the screen's top-left corner.
  - System mode polls the registry (`AppsUseLightTheme`) every 3 s with `after`, on the UI thread. A failed registry read counts as light; DWM failures are ignored.
- **`UpdateRunner` has no tkinter**: it reports through `report(line)` from its thread, and `UpdateDialog` hands each line to the UI with `after(0, ...)`. Close stays disabled until the job returns.
