# launcher.pyw

- **Child output must keep draining.** Each `Popen` uses `encoding="utf-8", errors="replace"` and `_stream_output` reads until EOF. If the reader thread dies (a decode error under Windows' cp1252 default can do this), the pipe fills and llama-server blocks on its next log line, which looks like the model hanging mid-chat.
- **tkinter is not thread-safe.** Background threads (readers, health poll, tray) must hand UI work to the main thread with `widget.after(0, ...)`.
- **Every launch command goes through `build_launch_command`**, which appends `--api-key-file` (ADR 0005). Don't start llama-server from anywhere else, and never ship a preset with any `--tools` or `--agent`: newer builds' built-in tools are only file, shell and OS tools that any web page could call, and an unknown tool name stops llama-server from starting (b11636 dropped `get_datetime`; ADR 0011).
- **The keys are never displayed** (only copied) and never written to `config.json`, whose contents the UVX proxy also reads. The approval key (`approval_key.txt`, ADR 0009) is created at startup next to the API key; only the Jobs panel sends it.
- **Auto preset:** `AUTO_COMMAND` must not set `-c` or `-ngl`; setting either turns `--fit` off for that value (ADR 0001). `load_presets` always replaces Auto with the code's version (a copy gets saved into `config.json` whenever presets are edited, and would otherwise go stale), and `_delete_preset` refuses to delete it.
- **Preset selection resets to Auto** on startup and on every model change; other presets are manual overrides and are not remembered (ADR 0002).
- **Preset `models` are case-insensitive substring keywords**, not exact filenames, even though the dialog stores full names. A short keyword like `"qwen"` matches every Qwen file.
- **Vision models:** an `mmproj*.gguf` is only paired with models in the same *subfolder*; one sitting in the root models folder is ignored. Display names come from the file name, and the first one found wins (root before subfolders, then alphabetical).
- **`_free_port` only kills our own leftovers** (`is_own_process`: any `llama-server.exe`, or a command line containing this folder's path). Anything else on 8080/8081/8001 aborts the launch with its name and PID; on 8002 it only skips the agents server. It runs `netstat` and a PowerShell CIM query on the UI thread, so the window stalls briefly when a port is taken.
- **mcp-proxy runs through `mcp_guard.py`** (`uv run --no-project --with mcp-proxy==0.13.0 python <this folder>\mcp_guard.py --named-server-config <this folder>\config.json ...`), so `is_own_process` recognises it by this folder's path. The wrapper adds the Host check mcp-proxy lacks by wrapping the app passed to `uvicorn.Config` (ADR 0012). Bumping the mcp-proxy pin means re-running the live probe: `Host: evil.example:<port>` must get 421.
- **`uvx_command` uses `{config}` and `{guard}` placeholders** for the config and wrapper paths, resolved at launch by `resolve_uvx_command`, so moving the folder doesn't break MCP. Saved configs keep their own command: `migrate_uvx_command` swaps only the exact old default (`uvx mcp-proxy ...`) for `UVX_COMMAND`, and an edited command stays unguarded.
- **The agents server is a fourth process the launcher starts itself** (`_start_agents_server`, after the UVX proxy): `uv run --script agents\server.py --port 8002`, list args with `CREATE_NO_WINDOW` (no shell, so nothing else hides uv's console), cwd = this folder. Its lines go to the UVX pane prefixed `[agents] `, and `health_status` names it "agents server". It used to run inside mcp-proxy, where one failure killed fetch and ddg-search too (ADR 0007). `remove_stale_agents_entry` deletes the old `agents` entry from `config.json`'s `mcpServers` on launch.
- **`_kill_all` cancels unfinished agent jobs last, after all four processes are dead** (the agents server is killed before `cancel_unfinished`). Only once it's gone is the launcher the sole writer of job files. The call is wrapped so a failure there (unreadable sandbox) can't stop the exit.
- **The agents feature is optional: sandbox or `agent_folders.json` errors must never stop the launcher from starting or exiting.** `ensure_dirs` at startup catches `OSError` into `_agents_error` (then the agents server isn't started), `_start_agents_server` logs any failure (port held by a stranger, no `uv`) and lets the launch carry on, `FoldersDialog` shows its own I/O errors, and `_kill_all` swallows the job cleanup. `FoldersDialog` is a child of Settings and its `_close` hands the grab back to Settings (Tk doesn't restore it on destroy).
- **Health:** `health_status` reports a crashed child by name before anything else; llama-server's `503` while loading shows as "loading model", not "offline". The agents server is optional, so its crash shows for one poll only (`shown`), then llama's status returns and the crash stays in the UVX pane as an `[agents] exited (code N)` line. Exit Processes stops the poll before killing, so its own kills aren't reported as a crash.
- `_kill_proc` uses `taskkill /T` because with `shell=True` the Popen PID is `cmd.exe`; `proc.kill()` would kill only the shell and leave llama-server running and holding VRAM.
- Log panes are never trimmed; a very long session makes the UI slower (not the model).
- **WinGet calls (llama.cpp updates):** every call passes `--source winget --disable-interactivity`, so a prompt makes WinGet fail instead of hanging. Only upgrade and install pass `--accept-package-agreements --accept-source-agreements`, and only after the user clicks Update or Roll back; the notice says updating accepts the package's terms. `check()` (list) runs at every start and must never accept anything.
- **Updates and roll back only while the servers are stopped:** Windows locks a running `llama-server.exe`. The Update button is disabled in the running state, and Settings gets `on_rollback=None` then.
- **The build check runs llama-server on spare port `18081`** (never 8081) and always kills it with `taskkill /F /T` in a `finally`, even on timeout or an exception; otherwise it keeps holding VRAM.
- **`previous_build` is the only update state** (`config.json`, `"b9776"`): set right before an update, cleared after a successful roll back so the startup notice offers the newer build again. A failed roll back leaves it, so Settings can retry.
- **`UpdateRunner` has no tkinter**: it reports through `report(line)` from its thread, and `UpdateDialog` hands each line to the UI with `after(0, ...)`. Close stays disabled until the job returns.
